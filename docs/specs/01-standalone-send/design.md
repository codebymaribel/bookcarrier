# Design — Feature 1: Standalone Send

See [requirements.md](./requirements.md) and [research.md](./research.md).

## Decisions from the research

- FanFicFare is installed with Homebrew and invoked as a subprocess; we trust its internal backoff on network errors/429 (see research.md).
- Telegram bot with **grammY** (long polling), for better documentation for someone starting with Telegram bots.
- `scp` as a subprocess via `spawn`, never `exec`, listening to the `error` event in addition to `close`.
- Stable file name `<fic-id>-<title>.epub`, **generated by FanFicFare** via `-o output_filename='${storyId}-${title}${formatext}'` (verified against FanFicFare 4.63.0 — see research.md). FanFicFare also sanitizes the name on its own with `output_filename_safepattern`, so we do not implement our own sanitization.

## Modules

```
src/
  config.ts         # loads and validates the external config file
  ao3-link.ts      # finds and validates the AO3 work link inside a message (T2)
  bot.ts             # grammY setup, owner filter, request flow (orchestration)
  messages.ts      # every text sent to the owner + failureMessage(): the single error → message mapping
  downloader.ts    # FanFicFare subprocess wrapper
  uploader.ts       # scp subprocess wrapper
  # (a filename.ts is no longer needed: FanFicFare generates the name, see below)
  logger.ts          # simple logger (from "step 0" scaffolding)
  index.ts            # entrypoint: wires everything up and calls bot.start()
```

### `index.ts` and how the daemon runs

- Loads the config (a `ConfigError` is logged with every wrong field and the process exits with code 1, R6.4), builds the bot, installs `bot.catch` (log and keep serving, instead of grammY's default of stopping), and starts long polling.
- `SIGINT` / `SIGTERM` call `bot.stop()` and the process exits with code **0**; a config error or a failed start (bad token, a second instance polling the same bot) exits with **1**. This is what launchd's `KeepAlive: { SuccessfulExit: false }` in feature 2 relies on: an intentional stop is not relaunched, a failure is.
- Node does not map `./x.js` imports to `.ts` files, so the daemon runs from compiled output: `pnpm build` (`tsconfig.build.json`, only `src` → `dist/`) and `pnpm start` (`node dist/index.js`). Feature 2's plist points at that same `dist/index.js`.

### `config.ts`

Reads a file (fixed path, e.g. `~/.bookcarrier/config.json`, outside the repo). Shape settled on 2026-11-17:

```ts
type Config = {
  // required
  telegramToken: string;
  ownerId: number;          // comes from Test 3
  kindleUser: string;       // "root" on a jailbroken Kindle
  kindleHost: string;       // IP or hostname only, WITHOUT the user
  sshKeyPath: string;

  // optional, with defaults in code
  downloadTimeoutMs?: number;      // default 600_000 (10 min)
  uploadTimeoutMs?: number;        // default 120_000 (2 min)
  sshConnectTimeoutSec?: number;   // default 10
  kindlePort?: number;             // default 2222 (KOReader's SSH, verified 2026-11-18)
  remotePath?: string;             // default "/mnt/us/documents/books/"
};
```

Why `kindleUser` is separate from `kindleHost`: putting `root@192.168.x.x` in a single string forces parsing it as soon as the host alone is needed (a log, a reachability check), and it is easy to get wrong. Separate, `config.example.json` also explains itself.

Why the default `kindlePort` is 2222 and not 22: this Kindle's SSH server is KOReader's, which listens on 2222 — 22 does not respond. Verified against the real device on 2026-11-18. If USBNetwork's sshd is ever enabled (which does use 22), it is overridden via config.

Why timeouts are config and not constants: they are field-tuning values. The KindleMOD lesson (scp at ~0.3 KB/s because of a hung Docker process) is exactly the case where a timeout needs to change without recompiling. The 2-minute `uploadTimeoutMs` is chosen to **detect** that pathology: at 0.3 KB/s an EPUB would take half an hour, and we prefer to fail and report rather than wait.

- Expands a leading `~` in `sshKeyPath` to the home directory (R6.5). Only that field: `remotePath` is a path on the Kindle, not on the Mac.
- Validates required fields at startup; if any is missing or has the wrong type, the daemon does not start and logs which one (R6.4).
- `config.example.json` in the repo with generic values (placeholders), never the real file.

### `bot.ts`

- Creates the grammY `Bot` with the token from config.
- Global middleware: if `ctx.from?.id !== config.ownerId`, it does nothing (R1.1) — it does not even reply, so as not to confirm to a stranger that the bot exists and is active.
- Gets the work id from the message through `ao3-link.ts` (R2.4–R2.6) and builds the canonical URL from it.
- Orchestrates: validates the link → creates the request's temporary directory → calls `downloader` (which already returns the EPUB path with the right name) → calls `uploader` → replies.
- **Owns the temporary directory.** `bot.ts` creates it with `mkdtemp` and removes it in a `finally`, whether the request succeeded or failed; otherwise every download would leave an orphan EPUB in `/tmp`. (Feature 2 replaces this with the spool.)
- Two exports besides `ownerOnly`: `createRequestHandler(config, deps?)` builds the function that handles one message (it never throws: every failure ends in one reply and one log line), and `createBot(config, deps?, grammy?)` wires `ownerOnly` first and a single `message:text` handler. `deps` (downloader, uploader, temp-dir creation/removal, logger) is injectable so the flow is tested without subprocesses or disk.
- A failed Telegram `sendMessage` is logged and ignored: it must not abort the fic's delivery.
- Texts to the owner are plain text (no `parse_mode`, so a title with `_` or `[` cannot break a message) and live in `messages.ts`, in English like the rest of the project. Changing the language is a one-file change.
- Non-text messages from the owner (photos, stickers…) are ignored.
- **Sequential by design.** `bot.start()` handles updates one at a time, so the handler simply `await`s the download and the upload. Nothing blocks the event loop (all I/O is async), but a second message waits for the first to finish. This is accepted for feature 1 (see requirements Scope); feature 2's queue removes it.

### `ao3-link.ts`

```ts
type LinkResult =
  | { ok: true; workId: string; canonicalUrl: string }
  | { ok: false; reason: 'no-ao3-link' | 'unsupported-link' };

function extractWorkLink(text: string): LinkResult;
```

- Splits the text into URL candidates (`https?://` up to whitespace), parses each with `new URL()` and keeps the first whose hostname is exactly `archiveofourown.org` or `www.archiveofourown.org` (R2.4, R2.5).
- `'no-ao3-link'` → R2.2 (no URL at all, or only URLs from other sites). `'unsupported-link'` → R2.3 (an AO3 URL that is not an individual work: series, collection page, user page…).
- `canonicalUrl` is `https://archiveofourown.org/works/<workId>` (R2.6).
- Pure function, no I/O: that is what makes T2 trivial to test.

### `downloader.ts`

- Signature (settled 2026-11-17):

  ```ts
  type DownloadOptions = { timeoutMs: number };
  type DownloadResult = { filePath: string; title: string };

  function downloadEpub(url: string, outDir: string, opts: DownloadOptions): Promise<DownloadResult>;
  ```

  It takes an options object, not the whole `Config`: it needs a single value, and this way the test does not have to build a full config. `bot.ts` maps config → opts. The `ficId` is **not** returned: the caller already has it from T2's parsing, and having it in two places opens the door to them differing.
- Uses `child_process.spawn('fanficfare', [url, '-f', 'epub', '--non-interactive', '-o', "output_filename=${storyId}-${title}${formatext}"], { cwd: outDir, stdio: ['ignore', 'pipe', 'pipe'] })`, never `exec` (avoids an intermediate shell). `--non-interactive` and the closed stdin are R3.6. Note: the `${...}` is a FanFicFare template, not a JS one — in TypeScript it goes as a string literal, not a template string.
- `outDir` is an **empty temporary directory exclusive to this request**. After the process closes successfully, we look for the only `*.epub` left there: this way there is no need to predict the name or reimplement FanFicFare's safepattern. If there are zero or more than one `.epub`, it is an error.
- Resolves the promise when the process closes with code 0 **and** the resulting file can be confirmed with size > 0 (R3.2).
- Listens to `'error'` (the subprocess could not be launched: `ENOENT` because `fanficfare` is not installed or not resolvable in the PATH → R3.5) separately from `'close'` (non-zero exit code → failed download → R3.3). Same structure as `uploader.ts`, and for the same reason: they are two different kinds of problem, and in feature 2 that difference decides whether the request is queued.
- The two failure classes are `DownloadFailedError` (`reason`: `exit-code` | `timeout` | `no-file` | `multiple-files`) and `DownloadLaunchError` (carries `binary`). On a non-zero exit the message holds only the **last non-empty line** of stderr (capped), because FanFicFare prints a Python traceback whose useful part is the final exception line; the whole tail (2000 chars) is kept in `DownloadFailedError.stderr` for the logs. The owner never sees a stack trace.
- On timeout the process is killed with `SIGKILL` (there is nothing to clean up gracefully: `outDir` is disposable).
- The `'error'` error names the binary it did not find, so a badly built PATH under launchd is recognized right away (see R7.5 of feature 2).
- Rejects the promise if: non-zero exit code, own timeout exceeded (R3.4), or the expected file is not found after closing (R3.3).
- **The `title` is a display title, best-effort.** The contract does not promise where it comes from, and that is on purpose: it decouples the (a)/(b) decision from the signature.
  - **T4 implements (a):** derive it from the resulting file name, stripping the `<storyId>-` prefix and the extension. It is free, adds no request to AO3, and the name is already generated by FanFicFare.
  - **(b) stays as a later improvement:** a prior step with `-m`/`--meta-only` to get the unsanitized title. It will be decided after seeing a real Telegram message with an accented-title fic — if `Coraz_n partido` is a nuisance, the inside of `downloadEpub` is changed without touching its signature or `bot.ts`.
  - That is why **this does not block T4**: the decision is about the quality of the string, not the shape of the contract.

### File name (no longer needs its own module)

R4.1 and R4.2 are fulfilled by FanFicFare: we pass it the template `${storyId}-${title}${formatext}` and it applies its own `output_filename_safepattern` (replaces with `_` everything that is not `a-zA-Z0-9_. []()&'-`). We write no sanitization of our own: duplicating it only opens the door to it falling out of sync with FanFicFare's.

What does need testing is that we *ask* for the template correctly and that we *find* the resulting file — that lives in `downloader.ts`.

### `uploader.ts`

- Signature (corrected 2026-11-17 — it used to say `config: Config`, which was wrong: in `Config` the optional fields are `undefined`, so `remotePath` might not exist):

  ```ts
  type UploadOptions = {
    sshKeyPath: string;
    kindleUser: string;
    kindleHost: string;
    port: number;
    remotePath: string;
    connectTimeoutSec: number;
    timeoutMs: number;
  };

  function uploadToKindle(localPath: string, opts: UploadOptions): Promise<void>;
  ```

  Same criterion as the downloader: explicit fields instead of the whole `Config`, so the signature declares what it depends on and the test does not build a full config.
- **Mandatory prior step (R5.2):** before launching anything, `fs.stat` on `opts.sshKeyPath`:

  ```ts
  const usableBySsh = (mode: number) =>
    (mode & 0o077) === 0 &&   // neither group nor others have anything: SSH's criterion
    (mode & 0o400) !== 0;     // and the owner can read it (covers the 000 edge case)
  ```

  SSH's criterion is used, not exactly `600`: a `400` key is valid for SSH and rejecting it would invent a failure in a configuration that works. If it fails, the send is rejected without spawning, with an error naming the problem (missing / open permissions / unreadable by the owner).

  **Out of scope on purpose:** SSH also verifies that the key belongs to the user using it (a key copied with `sudo` ends up owned by `root`). We do not check it: on a single-user Mac it is unlikely, and if it happens, it falls as a send failure and shows in the logs. If it ever becomes a nuisance, it is one more condition on the same `stat`.

  Why it goes first and is not detected afterwards: `spawn`'s `'error'` event **only** fires if the binary itself cannot be executed. With a missing key or open permissions, `scp` starts without problem, SSH warns on stderr, ignores the key and exits with a generic error code — the same one it gives when the host does not respond. Checking beforehand is deterministic and does not tie us to OpenSSH's messages.

- Invocation (`connectTimeoutSec` and `remotePath` come from `opts`, already resolved with their default):

  ```ts
  spawn('scp', [
    '-P', String(opts.port),
    '-o', `ConnectTimeout=${opts.connectTimeoutSec}`,
    '-o', 'BatchMode=yes',
    '-i', opts.sshKeyPath,
    localPath,
    `${opts.kindleUser}@${opts.kindleHost}:${opts.remotePath}`,
  ]);
  ```

  `BatchMode=yes` (R5.6) prevents an authentication failure from waiting for a password.

  **Uppercase `-P` (R5.8).** In `scp` the port is `-P`; lowercase `-p` preserves file timestamps and leaves the port at 22. It is a silent mistake: the invocation looks valid and fails as if the Kindle did not respond.

- Listens to `'error'` (the binary could not be executed: `ENOENT` / `EACCES` → R5.5, names `scp`) separately from `'close'` (any non-zero code → send failure → R5.3).
- **No logic is built on `scp`'s exit code (R5.7).** OpenSSH codes are generic and the same value covers unreachable host and rejected authentication. Everything permanent has already been filtered out beforehand: the key by the `stat`, the binary by the `'error'` event.
- Known and accepted limitation: if the key is a valid file but the Kindle rejects it (for example, `authorized_keys` deleted), that falls as a send failure. In feature 2 it will be retried for 30 minutes in vain and then reported. It is acceptable: it does not justify parsing stderr, which is fragile.
- Own timeout in addition to SSH's `ConnectTimeout`, in case the process still hangs. On timeout the process is killed with `SIGKILL`.
- Two error classes: `UploadConfigError` (`problem`: `key-missing` | `key-permissions-open` | `key-unreadable` | `binary-not-found`; permanent) and `UploadFailedError` (`reason`: `exit-code` | `timeout`; carries `stderr` for the logs). The message of a send failure holds the **last two** non-empty stderr lines, because OpenSSH prints the cause and `scp` then adds a generic `scp: Connection closed`.

### End-to-end error handling

All error paths end at a single point that writes the owner a clear Telegram message (no stack traces), distinguishing at least: unrecognized link, download failure, send failure because the Kindle is unreachable, send failure because of broken configuration (key/PATH).
